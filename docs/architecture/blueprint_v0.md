## 一、定位与设计理念

本文档是具身智能实验室的**核心工程契约**。
它不涉及具体场景算法，也不定义底层的代码结构（如 ROS2 Message 字段）。它的核心目的是：**通过系统架构的切分，解决物理试错成本高、硬件异构性强、团队协作复杂的痛点。**

所有后续的具体技术实现（如 P2 的网络架构与 ROS 接口、P3 的安全 SOP 与场地设计）均须遵循本文档定义的边界与约束。

---

## 二、系统层级模型 (System Layer Model)

系统自下而上分为六层。**核心约束**：上层可以调用下层提供的标准服务，严禁跨层调用（例如：L5 的算法节点严禁直接调用 L2 的硬件 SDK）。

```
┌─────────────────────────────────────────────────────────┐
│ L6 组织与流程  RACI · SOP · 实验流程 · CR              │
├─────────────────────────────────────────────────────────┤
│ L5 系统流水线  Perception → Plan → Skill → Safety      │
├─────────────────────────────────────────────────────────┤
│ L4 数据与实验  run_id · rosbag2 · index · metadata     │
├─────────────────────────────────────────────────────────┤
│ L3 软件中间件  ROS2 Humble · DDS · launch · interfaces  │
├─────────────────────────────────────────────────────────┤
│ L2 硬件与运维  台账 · 点检 · 驱动桥 · 标定              │
├─────────────────────────────────────────────────────────┤
│ L1 空间与设施  场地 · 分区 · 网络 · 安全设施            │
└─────────────────────────────────────────────────────────┘
```

## 三、统一流水线逻辑 (Unified Pipeline Logic)

**设计依据 (Rationale)**：早期 Demo 往往将感知、规划、控制耦合，导致团队规模扩大时无法并行开发。本架构强制切分输入输出边界。

```
                    ┌──────────────┐
                    │  Task/调度   │  （框架期：人工+launch；后期：状态机）
                    └──────┬───────┘
                           ▼
┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│ Perception  │───▶│    Plan     │───▶│    Skill    │───▶│   Safety    │
│   (感知)    │    │   (规划)    │    │   (技能)    │    │   (安全)    │
└─────────────┘    └─────────────┘    └─────────────┘    └──────┬──────┘
       ▲                                                          │
       └──────────────── 人工接管 / 急停 / 降级 ◀─────────────────┘
```

**模块语义契约（P2 需据此设计具体的 ROS2 Topic）：**
1. **Perception**：只输出“世界状态”（如物体位姿、障碍物点云）。
2. **Plan**：接收感知与任务，只输出“意图轨迹”（如空间路径、目标关节角）。
3. **Skill**：接收轨迹，转换为具体的“控制指令”（如关节力矩、速度向量）。
4. **Safety**：接收全链路状态，输出最终的“安全状态许可”。

## 四、数据流与追溯原则 (Data Flow & Traceability)

**设计依据 (Rationale)**：具身实验高度依赖环境配置，缺乏关联的数据在事后无法用于复现和 debug。

1. **唯一主键 (`run_id`)**：任何物理设备的上电运行，必须绑定一个全局唯一的 `run_id`。
2. **血缘绑定**：`run_id` 必须强制关联：操作人、设备 ID、Git Commit Hash、参数配置快照。
3. **存储分层原则**：
   - 动态实验必须录制全量传感器与控制数据（rosbag）。
   - 系统需支持热数据（近期高频访问）与冷数据（归档追溯）的分层存储。
   - **P2 动作项**：P2 须在《网络与算力规划》中，基于总体方案中“最大 2 台设备并发”的基线，测算具体的存储吞吐与容量需求。

## 五、软硬安全接口 (Hardware-Software Interface, HSI)

**设计依据 (Rationale)**：鉴于机器人均为电池供电，无法通过切断外部市电来实现急停，安全机制必须依赖“网络软停+遥控器硬停+本体断电”的组合。

1. **全局软件急停 (Level 1)**：实验室操作台与安全门处的急停按钮，接入主控机的 GPIO。拍下时，Safety 模块向全网广播 `ESTOP`，驱动桥接收后执行软件级驻车（如双足趴下、机械臂锁死）。
2. **遥控器硬件阻断 (Level 2)**：动态实验时，安全员必须手持机器人专属遥控器。遇紧急情况，人为拨动遥控器上的掉电/失能开关，触发机器人底层硬件保护。
3. **本体物理断电 (Level 3)**：机器人机身上的物理急停按钮直接串联在电池输出端。在确保人员安全的前提下，按下可彻底切断动力电。
   - **P3 动作项**：P3 须在《安全 SOP》中明确这三级急停的触发时机与人员站位。

## 六、非功能性需求 (NFR) 指引

以下为系统必须满足的关键指标维度。**P2/P3 须在各自方案中给出明确的承诺值与实现手段：**

| NFR 维度 | 考核说明 | 后续承接方 |
|----------|----------|------------|
| **通信延迟 (Latency)** | 从 Skill 模块发出指令到驱动桥接收的端到端网络延迟上限（如：需保障 < 10ms）。 | P2 (网络规划) |
| **数据吞吐 (Throughput)** | 2 台设备并发动态实验时，网络与存储系统需支撑的峰值带宽（如：多路 4K 视频流的写入带宽）。 | P2 (算力规划) |
| **系统可用性** | ROS 主节点（如 lab-ws-01）崩溃时的恢复时间或容灾策略。 | P2 (平台架构) |
| **物理包络 (Envelope)** | 动态实验区需满足的最大机器人运动半径与净空高度。 | P3 (场地规划) |

## 七、设备接入原则 (Driver Bridge)

**设计依据 (Rationale)**：实验室拥有多品牌异构硬件，若算法直连厂商 SDK，将导致代码无法复用。

1. **驱动桥隔离**：所有厂商原始 SDK 必须被封装在“驱动桥（Driver Bridge）”之下。
2. **通用指令**：上层算法仅下发标准“通用技能指令”，由驱动桥翻译为底层专有协议。
   - **P2/P3 动作项**：输出《设备驱动 Gap 分析》，并在 W3 完成至少 1 个设备（建议 franka-01）的驱动桥 PoC 验证。
